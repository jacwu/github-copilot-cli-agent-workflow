# Task 1: Initialize Project Scaffold and Global UI Style Configuration

## Background

The repository-level requirements and technical design define a travel website built on Next.js 15, TypeScript, Tailwind CSS, and shadcn/ui, with a deliberately visual-first "Light & Airy Vacation Style." This first task establishes the frontend baseline that all later pages and components will inherit.

Issue #7 focuses on project initialization and global UI style configuration rather than feature delivery. The outcome of this task should provide a clean, consistent scaffold for future authentication, destination discovery, trip planning, and about-page work without forcing later tasks to revisit foundational setup decisions.

## Goal

Create the technical foundation for the application by:

- initializing a Next.js App Router project with TypeScript,
- enabling Tailwind CSS for utility-first styling,
- integrating shadcn/ui so later tasks can build on a shared component system,
- defining global design tokens and base styles that enforce the "Light & Airy Vacation Style," with Ocean Teal as the single primary accent,
- establishing layout and style conventions that make subsequent frontend work predictable and visually consistent.

## Non-Goals

This task does not include:

- implementing product features such as authentication, destinations, trips, or about-page content,
- building completed page UIs beyond the minimal scaffold needed to verify global styling is wired correctly,
- defining backend, database, or API behavior beyond what is already captured in the repository design document,
- introducing multiple branded accent colors or a theme-switching system,
- finalizing every reusable component variant that later tasks may need.

## Current State

At the start of design, the repository contains product documentation and task metadata, but no confirmed application scaffold or issue-level design for this task. The repository-wide technical design already specifies the intended stack and visual direction:

- frontend framework: Next.js 15 with App Router,
- language: TypeScript with strict typing,
- styling: Tailwind CSS plus shadcn/ui,
- visual language: light backgrounds, generous whitespace, large radii, soft shadows, and Ocean Teal as the primary identity color.

Because this is the first implementation task, decisions made here will directly affect file layout, shared styling primitives, and the ergonomics of all later frontend tasks.

## Proposed Design

### 1. Project scaffold

The application should be scaffolded as a Next.js 15 App Router project using TypeScript and npm. The initial structure should align with the repository-level design, especially the `src/app`, `src/components`, and `src/lib` organization.

Recommended initial structure for this task:

```text
src/
  app/
    favicon.ico (optional if generated by scaffold)
    globals.css
    layout.tsx
    page.tsx
  components/
    ui/
  lib/
    utils.ts
```

This task should establish only the baseline directories and files needed for styling and later component reuse. Feature-specific route groups and domain modules should remain for later tasks.

### 2. Tailwind CSS baseline

Tailwind should be configured as the global styling system for the app. The configuration should support:

- scanning the `src` tree for class usage,
- using CSS custom properties as theme tokens where practical,
- applying Tailwind utilities consistently across App Router pages and shadcn/ui components.

The main styling entry point should be `src/app/globals.css`, which will contain:

- Tailwind base/component/utility imports appropriate to the selected Tailwind version,
- root-level CSS variables for colors, radii, and elevation,
- base element styling for `body`, headings, links, and focus states.

### 3. shadcn/ui integration approach

shadcn/ui should be installed and configured early so later tasks can add UI primitives without reworking aliases, Tailwind wiring, or shared utilities.

The integration should include:

- a valid component alias setup compatible with the project tsconfig,
- a shared `cn` utility in `src/lib/utils.ts` for class composition,
- a base shadcn style preset that respects the project token system instead of introducing conflicting theme values.

The design expectation is not to add many generated components in this task. Instead, this task should ensure the repository is ready for later components such as buttons, cards, inputs, dialogs, and navigation primitives.

### 4. Global design token system

The visual system should be defined through a small set of global CSS custom properties, then consumed through Tailwind/shadcn-compatible styles.

#### 4.1 Color tokens

Ocean Teal is the only primary accent and should be used for:

- primary buttons,
- interactive highlights,
- links and focus emphasis,
- selected/filter-active states,
- key calls to action.

The token model should distinguish between semantic roles rather than hard-coding color values directly in components.

Recommended token categories:

- `--background`: main page background, near-white,
- `--foreground`: primary text,
- `--card`: card/surface background,
- `--card-foreground`: text on cards,
- `--muted`: subdued surface background,
- `--muted-foreground`: secondary text,
- `--border`: low-contrast border tone,
- `--input`: input surface/border tone,
- `--primary`: Ocean Teal,
- `--primary-foreground`: contrasting foreground used on teal surfaces,
- `--ring`: focus ring aligned to Ocean Teal.

The palette should stay intentionally restrained. Beige and soft gray may appear as neutral support tones, but they should remain background/surface values rather than secondary brand accents.

#### 4.2 Radius tokens

The design document explicitly calls for large radii. Global tokens should default surfaces toward a softer, friendlier shape language.

Recommended approach:

- define a base radius token mapped to a large default,
- ensure common surface components naturally land near `rounded-2xl`,
- reserve `rounded-3xl` for more prominent containers such as hero cards, drawers, or modal shells.

This avoids inconsistent ad hoc radius choices across future tasks.

#### 4.3 Shadow tokens

The site should rely on soft elevation rather than strong borders. Global shadow values should therefore emphasize subtle depth and airy separation.

Recommended usage tiers:

- base surface shadow for cards and floating sections,
- slightly stronger interactive hover shadow,
- restrained use of heavier elevation only for overlays or emphasized callouts.

Shadow color and opacity should remain soft enough to preserve the calm travel aesthetic.

### 5. Global base styles

`src/app/globals.css` should set the visual defaults for the entire app.

Recommended base rules:

- `body` uses the global background token, foreground token, modern sans-serif font, and generous line-height,
- selections, focus rings, and anchor emphasis use the primary color family,
- default section spacing should feel open and breathable,
- borders should be low-contrast and optional, not the dominant separation mechanism,
- cards and panels should favor rounded corners plus shadow instead of sharp outlines.

A minimal root page can be used only to verify these styles are applied consistently from the start.

### 6. Layout foundation

The root `layout.tsx` should provide the application shell for future pages. At this stage it only needs to establish:

- global stylesheet import,
- metadata baseline if desired by the scaffold,
- outer document/body classes that apply background color, text color, and font,
- a neutral content container strategy compatible with later navigation and page sections.

The layout should avoid introducing feature-specific navigation or authentication state handling in this task.

### 7. Accessibility and UX baseline

Even though this task is style-focused, the design should bake in accessible defaults:

- focus-visible outlines/rings should remain clearly visible against pale backgrounds,
- color contrast for Ocean Teal text/buttons must remain readable on light surfaces,
- large radii and soft shadows should not reduce affordance clarity,
- hover-only affordances should always have a non-hover baseline state,
- typography and spacing should preserve readability across desktop and mobile viewports.

### 8. Expected configuration surfaces

Implementation should likely touch only the configuration and foundation layers needed for the scaffold. Expected surfaces include:

- `package.json` and npm-managed dependencies for Next.js, TypeScript, Tailwind CSS, and shadcn/ui,
- TypeScript path alias configuration,
- Tailwind/PostCSS configuration as required by the selected versions,
- `components.json` or equivalent shadcn/ui configuration,
- `src/app/globals.css`, `src/app/layout.tsx`, and a minimal `src/app/page.tsx`,
- `src/lib/utils.ts` for shared class utility support.

The exact generated file set may vary slightly depending on tool versions, but the implementation should keep the result close to the repository-wide intended structure.

## Implementation Plan

1. Scaffold a new npm-based Next.js 15 App Router project with TypeScript in the repository, preserving the repository's expected `src`-based layout.
2. Install and configure Tailwind CSS for the scaffolded app, ensuring global styles are driven from `src/app/globals.css`.
3. Install and initialize shadcn/ui with aliases and utility helpers compatible with the project structure.
4. Define the global CSS custom properties for semantic color roles, Ocean Teal primary styling, large radii, and soft shadow behavior.
5. Apply the tokens to base document styles in `layout.tsx` and `globals.css` so the app immediately reflects the Light & Airy Vacation Style.
6. Add only the minimal starter page/surface needed to validate that the scaffold, tokens, and global style system are wired correctly.
7. Verify the generated scaffold and configuration remain aligned with the repository-level architecture, leaving domain-specific features for subsequent tasks.
